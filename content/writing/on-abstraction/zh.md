在刚入行的头两年，我对代码里的“重复”有一种生理层面的洁癖。

只要在不同文件中看到五行相似的逻辑，或者两个组件拥有几个命名相近的 Props，我脑海中就会立刻拉响警报。随之而来的，是一场自我感动的重构：定义泛型基类、提取公共 Helper、封装 `UniversalDataGridContainer`。在当时的认知里，代码行数越少、复用度越高，就越代表自己掌握了高阶工程的精髓。

直到工作到第五年、第七年，亲手埋葬过几个由于“过度抽象”而彻底僵化的大型模块之后，我才真正参透了 Sandi Metz 在《Practical Object-Oriented Design》里那句振聋发聩的名言：

> **“重复远比错误的抽象廉价得多（Duplication is far cheaper than the wrong abstraction）。”**

今天的我，在面对重构和抽象时，变得前所未有的保守与迟钝。

---

## 一、偶然的一致性：最致命的抽象诱饵

为什么我们如此容易掉进过早抽象的陷阱？因为人类大脑极度擅长模式识别，我们太容易把**“偶然的一致”**误当作**“本质的规律”**。

设想这样一个极其常见的业务场景：

1. 业务上线了“用户端商品评价”功能，包含打分、文字评价、图片上传。
2. 两周后，运营提需求要求增加“售后工单用户满意度回访”，同样包含打分、文字反馈和图片上传。

此时，热衷 DRY（Don't Repeat Yourself）的工程师往往会两眼放光：“这不就是同一个东西吗？”于是，一个名为 `FeedbackModal` 的通用组件被抽象了出来。

```typescript
// 早期抽象：看似完美兼顾了两者
interface FeedbackModalProps {
  type: 'review' | 'ticket';
  targetId: string;
  onSubmit: (data: FeedbackPayload) => Promise<void>;
}
```

灾难在接下来的三个月里如约而至：

- 评价业务需要支持匿名提交、敏感词实时高亮；
- 工单业务需要支持满意度原因多选、必须强制关联客服工号；
- 评价业务需要接入晒单返券营销组件；
- 工单业务要求在打低分时弹窗二次挽留。

为了在同一个抽象中满足两个完全不同业务域的诉求，这个最初清爽的组件开始被动感染：

```typescript
// 三个月后的抽象怪物：千层饼布尔开关
interface FeedbackModalProps {
  type: 'review' | 'ticket';
  targetId: string;
  allowAnonymous?: boolean;
  highlightSensitiveWords?: boolean;
  showAgentSelector?: boolean;
  satisfactionReasons?: string[];
  couponBanner?: ReactNode;
  interceptLowScore?: boolean;
  // ... 还有 12 个布尔开关和回调
}
```

原本互不相干的两条业务线，被一层脆弱的“通用抽象”死死捆绑在一起。修改评价的逻辑，会导致工单测试用例全线飘红；想要理清某一个业务分支的执行流，必须在大脑中同时解析七八个三元运算符。

**它们在表面形态上的重合，仅仅是生命周期早期的巧合；它们改变的原因（Reason to Change）完全不同。** 将偶然一致的事物强行抽象，本质上是在用软件架构的复杂性，为短暂的代码复用买单。

## 二、错误抽象的隐性代价：认知负债的滚雪球

如果只是多写几个 if-else，或许还谈不上灾难。过早抽象真正危险的地方在于**认知污染与沉没成本**。

1. **接口契约一旦建立就具有粘性**：新加入团队的工程师会天然预设“前人抽象的模块必然代表了架构最佳实践”。即使他们察觉到别扭，也会优先选择在既有基类上加参数、打补丁，而不是掀桌重写。
2. **重构的心理阻力几何级增加**：删除 50 行重复的代码毫无心理负担；但要重构一个被全工程 20 处调用的“通用中间层”，需要协调跨团队的回归测试与灰度验证，阻力大到让所有人望而却步。
3. **隐藏了系统的真实复杂度**：错误的抽象就像一层刷在承重墙上的白漆，掩盖了底层领域模型不清晰的结构性裂缝。

## 三、“三次复用原则”（The Rule of Three）的工程落地

为了治好团队内部的“过早抽象狂热症”，我们在代码评审（Code Review）中贯彻了明确的**三次复用原则**：

```text
[场景 1 出现] ──> 专注直白交付，容忍内联逻辑
                   │
[场景 2 出现] ──> 允许显式复制，观察两条业务线的独立演进
                   │
[场景 3 出现] ──> 拥有三个真实样本，萃取真正的不变式与自由度
```

### 1. 第一次遇到：最简内联

遇到新需求时，写最直接、最清晰的代码。哪怕它只为当前场景服务，哪怕里面有硬编码的枚举。不要为未经验证的“明天可能要扩展”花费哪怕十分钟的脑细胞。

### 2. 第二次遇到：允许显式重复

当第二个相似需求来临时，克制住立刻抽象类或高阶组件的冲动。直接复制一份核心逻辑，并在各自的上下文里自由演化。

让代码在真实业务中奔跑一个月。观察它们是趋同演进，还是在两周后因为各自业务维度的分化而渐行渐远。**复制粘贴是探索领域模型边界成本最低的试验田。**

### 3. 第三次遇到：拥有真实样本后的精准提炼

当第三个相同形态的诉求出现时，你手里已经有了两份经过生产环境洗礼的成熟实现。此时，你不再是在脑海中“盲人摸象”，而是握有清晰的对照表：

- **不变式（Invariants）**：在所有三处都保持绝对一致的逻辑（例如底层的网络重试、签名哈希算法）。
- **自由度（Degrees of Freedom）**：因场景而异的展示层逻辑、字段映射与回调。

此时展开抽象，提炼出的接口才会恰如其分，像量体裁衣般严丝合缝。

## 四、好抽象的三个物理特征

如果必须进行抽象，什么样的抽象才不容易腐化？

### 1. 组合优于继承（Composition over Inheritance）

继承是刚性的，基类的任何一点变动都会波及整棵子类树。而函数组合与 React 常见的 Children 插槽是柔性的：

```typescript
// 脆弱的抽象：通过继承覆写方法
class BaseDataExportController { ... }

// 坚韧的抽象：通过流水线管道组合纯函数
const transformAndExport = pipe(
  fetchRawData,
  applyDomainFilter,
  formatToCsv,
  uploadToS3
);
```

### 2. 窄接口与单一关注点（Narrow Interfaces）

一个设计良好的接口通常很小。只暴露调用方必须知道的最小契约。不要设计一个拥有 20 个可选参数的“瑞士军刀函数”，宁可设计 3 个参数明确、语义清晰的独立小工具。

### 3. 永远预留逃生舱（Escape Hatches）

不要试图把底层逻辑封装成滴水不漏的黑盒。

举个实际例子：当你二次封装一个 `ApiClient` 时，永远在配置项中暴露一个 `customFetch?: typeof fetch` 或原生的 `headersInit` 逃生舱。一旦业务遇到跨域携带特殊探针 Header、或临时关闭某次请求的缓存时，开发者可以通过逃生舱直达底层，而不是被迫修改你的顶层封装库。

---

## 五、结语：克制是最高阶的工程直觉

回顾七年的编码历程，我的心态发生了一个有趣的闭环：

- **初学者**：写最直白的代码（因为还不会抽象）；
- **进阶者**：写最复杂的抽象（因为急于证明自己的设计模式与架构能力）；
- **成熟期**：重新写最克制直白的代码（因为敬畏系统的演进规律与代码的生命周期）。

优秀的架构师不是看他能设计多么庞大复杂的概念迷宫，而是看他能在混乱未定的业务浪潮中，保持多大程度的克制与定力。

下一次当你忍不住想创建一个通用的 `BaseFactoryManager` 时，不妨先深呼吸，把代码复制一份，让子弹再飞一会儿。
